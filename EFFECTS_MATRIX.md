# Effects matrix

The canonical capability list is in `GOAL.md` section 10. The row-by-row implementation, automated-test, and device/listening status is tracked in [`IMPLEMENTATION_CHECKLIST.md`](IMPLEMENTATION_CHECKLIST.md). No effect is considered shipped merely because it appears in the catalog or UI.

For each implemented processor, record: stable ID/version; category and exact function; source revision and license; channel layout; parameters/defaults/units; sample rates; latency; tail and bypass policy; quality modes; resource cap; measured per-block CPU percentage; automated evidence; and manual listening/hardware evidence.

## Channel-layout utility (UTL-04)

`convert_channels` handles interleaved mono/stereo float audio outside the `Effect` interface because conversion can change buffer length. It copies same-layout data, duplicates mono into left/right, and supports average or equal-power stereo summing. The default average is conservative for correlated content; equal-power may exceed full scale and adds no limiter. Only 1↔2 channels are supported. Invalid layouts, incomplete input frames, undersized output spans, and partial overlaps fail without modifying output; exact-start in-place conversion is supported. The operation is stateless, has no owned memory or algorithmic latency, and performs no allocation. Linux 48 kHz stereo/128-frame benchmark: stereo→mono average p50/p95 0.0015/0.0019%, stereo→mono equal-power 0.0015/0.0019%, mono→stereo 0.0023/0.0038% of the 2.667 ms block deadline. CTest, offline CLI, browser/WASM startup self-check, and Windows cross-build cover the implementation; live hardware and listening remain open.

## Parallel routing utility (UTL-05)

`split_to_parallel` copies mono/stereo interleaved float frames into two caller-owned branch buffers. `ParallelMixer` combines dry audio with two branch inputs using independent branch/dry gains, linear stereo balance and per-branch polarity inversion. Dry-only is the safe default. Gain, balance, and polarity changes ramp over 10 ms by default (configurable); mono ignores balance. The splitter and mixer are stateless with respect to audio history, add no algorithmic latency, perform no allocation, and reject invalid layouts, incomplete frames, undersized buffers, or partial overlap; exact-start input/output aliasing is supported where documented. Mixer state is 112 B; split uses 0 B. CTest covers mono/stereo copies and mix, dry default, gains, balance, phase inversion, variable-block ramps, bounds, alias rules, invalid input, and allocation count. The WASM startup self-check covers split and phase-mixed output. Linux 48 kHz stereo/128-frame p50/p95 is 0.0026/0.0030% for split and 0.0060/0.0064% for mix. These are low-level utilities only: they are not yet connected to the preset graph/editor or live routing scheduler. Windows cross-build passes; browser parity currently checks startup behavior rather than user-created parallel routes. Manual hardware/listening remains open.

## Chromatic tuner utility (UTL-09)

The tuner analyzes a mono sum of the unprocessed input through a decimated, fixed-storage YIN-style difference search. Its candidate pitch range is 50–1500 Hz, with an adjustable A4 reference from 400–480 Hz (default 440 Hz); this is not polyphonic note detection or pitch shifting. Synthetic native tests pass at 55 Hz, 1500 Hz, and low E2; behavior at the 50 Hz boundary and on real guitar/polyphonic input remains unverified. At 48 kHz the analysis window is 1,024 samples at 12 kHz (85.3 ms), with bounded analysis work spread across audio callbacks. It adds no algorithmic delay to audible processing. Optional output mute is applied after the output limiter so it also silences delay tails, and transitions ramp over 10 ms. The Linux tuner state is 10,400 B; the WASM tuner object reports 10,364 B and is included in the browser chain total. On the Linux 48 kHz stereo/128-frame benchmark it uses 0.0139% p50, 0.5760% p95, and 1.2252% maximum of the 2.667 ms callback deadline; transient peaks reflect the bounded analysis batches. Native tests cover note/frequency/cents, low E2, reference limits, silence, stereo, mute ramps, and zero allocations. The browser test checks decoded local audio, processed Play output, WASM A4 detection against a 432 Hz reference, and the rendered A4 readout; this synthetic case returned in 120.9 ms on HeadlessChrome 151. Human guitar/noise tracking and physical-device mute/listening checks remain open.

## Remaining evidence

The browser chain exposes independent block bypass, global dry bypass, input mute, and panic mute. Global bypass and input mute use 10 ms ramps; panic mute is immediate with a 10 ms fade-in on release. The shared control object and complete signal-control path are covered by automated tests and benchmarked in [`LATENCY_AND_QUALITY.md`](LATENCY_AND_QUALITY.md).

- Native Linux offline rendering and the local prerecorded-guitar corpus pass through Input Gain, Volume Pedal, High-pass, Low-pass, Gate, Pedal Compressor, Studio Compressor, Wah, Envelope Wah, Clean Boost, Soft Drive, Tremolo, EQ, Delay, Output Gain, and Peak Limiter. The regression checks the limiter ceiling, retains summary metrics, and removes temporary audio after the run.
- Linux desktop processor CPU and owned-memory figures are recorded in [`LATENCY_AND_QUALITY.md`](LATENCY_AND_QUALITY.md). Re-measure on each target CPU and after DSP changes.
- Human listening, native full-duplex hardware, Android, Windows runtime/audio, presets, live graph switching, and the broader effect catalog remain unverified or unimplemented. The browser/WASM test page and automated comparison pass, but manual audible-output/listening verification remains open. Its current AudioWorklet CPU timer is coarse. A passing offline render does not establish live performance or listening acceptance.
