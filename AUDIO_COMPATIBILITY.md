## Offline prerecorded audio

`make audio-fixtures-verify` passed for both external archives and the ignored local symlink `testdata/reference_audio`:

- EGFxSet Clean: 690 mono WAV files, one Strat and five positions (bridge, bridge-middle, middle, middle-neck, neck). The regression compares the same open high-E sample (`1-0.wav`) in each position.
- Guitar-TECHS P3 music: 32 WAV files; the test uses `P3_music/audio/directinput/directinput_01.wav`, a 48 kHz stereo performance excerpt. The dataset-level setup lists Player 3's Sire T7 with bridge-neck pickup selection; there is no separate per-file selector annotation.

`make audio-regression` passed on 2026-11-21. It rendered the five EGFxSet pickup-position samples (about 5 seconds each) and the 72.5-second Guitar-TECHS DI excerpt through the complete 30-effect chain, including the five new compressor/EQ stages. The pickup samples rendered mono; the DI rendered in stereo and through the explicit average stereo-to-mono route. Every output stayed below the limiter ceiling and was checked for a successful render and non-empty float32 WAV; temporary rendered files were removed after the run. The EGFxSet neck file has 236,465 frames versus 240,000 for the other pickup files because its source data chunk contains fewer frames; its extra terminal zero padding byte is handled by the WAV reader. The regression renders normal, Tape Echo, and multi-head routing for each clean pickup and the stereo DI; average stereo-to-mono is also checked. Stereo ping-pong alternation remains covered by native CTest and a stereo CLI impulse test.

These results verify the deterministic offline Linux path only. No audio hardware, live backend, Android route, or Windows route has been probed.

## Signal controls

`SignalControls` is shared native C++ code used by the browser/WASM chain. It ramps input mute and global dry bypass over 10 ms, keeps global bypass separate from per-block enable toggles and the dry/wet mix, and applies panic mute immediately with a 10 ms fade-in when released. The focused CTest verifies ramp values, bypass restoration, panic silence/release, bounds, stereo processing, and zero allocations. The latest `make bench` measured 0.0015% p50 / 0.0023% p95 of a 2.667 ms stereo block deadline and 80 B of owned state on the Linux desktop. The browser UI routes toggle messages to the WASM controls; the automated browser parity fixture exercises neutral defaults. Manual toggle interaction and audible behavior remain open.

## Mono/stereo conversion

The shared `convert_channels` helper copies matching layouts, duplicates mono into stereo, and downmixes stereo to mono using the default arithmetic average `(L + R) / 2` or explicit equal-power `(L + R) / sqrt(2)`. Equal-power can exceed full scale; the converter applies no clipping or normalization. It accepts only 1- or 2-channel interleaved float audio and does not resample. It performs no allocation or state update; exact-start in-place conversion is supported while partial overlap is rejected. `tabletfx_offline render` exposes `--output-channels preserve|mono|stereo` and `--mono-sum average|equal-power`. `make test` checks both downmix policies and upmix output. The WASM module exports the same converter and runs an average-upmix/downmix self-check when its AudioWorklet starts. Latest Linux p50/p95 costs for 128-frame stereo blocks are 0.0015/0.0015% for average downmix, 0.0011/0.0015% for equal-power downmix, and 0.0030/0.0034% for mono upmix. Memory cost is 0 B persistent state; caller-provided scratch/output buffers are excluded.

## Input/output metering

The shared `LevelMeter` reports sample peak, RMS, channel count, frame count, non-finite sample count, per-block clipping, a clearable clip latch, and clipped-block count without allocating or locking. It flags digital samples at or above 0.999 full scale; this cannot detect analog clipping inside an interface. Input is measured before input trim/mute, and output after output gain and the optional peak limiter. Two meters occupy 72 B and together measured 0.0154% p50 / 0.0289% p95 of the 2.667 ms block deadline in the latest Linux desktop benchmark. The browser displays peak/RMS in dBFS, clip status, and invalid-sample/frame diagnostics. The automated headless test matched the input meter to the decoded local file and the output meter to the corresponding captured processed block; device-level clip behavior remains unverified.

## Parallel routing primitive (UTL-05)

The shared C++ core now provides an allocation-free two-branch splitter and a dry-plus-two-branch mixer with independent gains, stereo balance, phase inversion, dry-only defaults, and 10 ms control smoothing. It has no algorithmic delay; mixer state uses 112 B. Native CTest covers audio and buffer rules, the WASM module runs a splitter/mixer startup self-check, and `make windows-cross-build` compiles the same code for Windows. Latest Linux p50/p95 is 0.0019/0.0023% of a 2.667 ms stereo deadline for split and 0.0064/0.0071% for mix. This is a tested DSP primitive, not yet a graph-editor/live-routing feature. Browser automation currently verifies the module self-check; it does not expose user-built parallel branches. Native hardware behavior remains unverified.

## Browser/WASM playback

The browser test page for `WEB-01` reads a user-selected local audio file, processes it through the shared C++ DSP compiled as WebAssembly and hosted in an AudioWorklet, and routes Play output to the browser destination. Stop, rewind, block bypass controls, and dry/wet comparison are present. Audio stays local; the page has no microphone or upload path. The delay offers free-time milliseconds or tempo sync (20–300 BPM, 12 divisions), editable Slapback and Tape quick presets, selectable Digital/BBD/Tape character, tape saturation and linked wow/flutter controls, normal and ping-pong stereo routing, independent dual A/B lines, four-tap pattern mode with per-tap time, level, and pan, and a multi-head mode with selectable heads and spacing. The page also exposes optical/FET-style compressors, guitar/bass graphic EQ layouts, and low-shelf/high-shelf/tilt EQ. `make web-test` enables Tape coloration and the four-head pattern on the local-file Play capture and compares the 30-stage WASM chain with the native renderer. Its current guitar-like fixture is mono, so it validates effect parity and head timing but not stereo placement; native and stereo CLI tests verify equal-power panning, BBD isolation, and linked Tape modulation. The browser test keeps its fixture mono because the separate tuner path is verified against a mono A4 reference.

The browser test uses HeadlessChrome 151, 48 kHz mono, 128-frame blocks (2.667 ms deadline), and a generated one-second guitar-like fixture. Its 30-stage chain enables Input trim, Volume Pedal, High-pass, Low-pass, Noise Gate, Pedal Compressor, Studio Compressor, Wah, Envelope Wah, Clean Boost, Transparent Overdrive, Mid-focused Overdrive, High-gain Distortion, Round Fuzz, Soft Drive, Tremolo, Chorus, Flanger, six-stage Phaser, Vibrato, three-band EQ, four-tap Delay with Tape coloration and multi-head routing, Polyphonic Pitch Shifter (+5 semitones), Optical-style Compressor, FET-style Compressor, Guitar Graphic EQ, Bass Graphic EQ, Shelf/Tilt EQ, Output level, and Peak Limiter. Tape settings are 45% saturation, 0.35 ms / 0.30 Hz wow, and 0.08 ms / 6 Hz flutter. Taps use 180/240/360/480 ms, levels 65/45/30/20%, and pans hard-left/hard-right/25%-left/25%-right; the mono browser fixture centers their output. The fixture also selects transparent overdrive at 0.15 drive / −3 dB / 35% wet; mid-focused overdrive at 0.18 drive / +6 dB mid boost / −4 dB level / 40% wet; high-gain distortion at 0.75 drive / 100 Hz pre low cut / 9 kHz pre high cut / 5.2 kHz post tone / −9 dB level / 100% wet; Round Fuzz at 0.55 fuzz / −6 dB / 85% wet; negative flanger feedback; Phaser at 0.5 Hz / 250–1600 Hz sweep / 0.15 feedback / 20% wet; and Vibrato at 5 Hz / 0.35 ms depth / 35% wet. Browser capture differs from the native renderer by 0.00134609 maximum absolute error and 0.00008779 RMS error (0.4668% of reference RMS), within 6% peak and 7.5% RMS limits. The C++ chain reports 1,229,764 bytes plus 10,364 bytes for tuner state within the fixed 16 MiB WebAssembly heap. The browser fixture is generated test audio; `make audio-regression` renders the full 30-effect chain on five recorded pickup positions and a stereo prerecorded DI performance, with separate Tape Echo and multi-head passes.

The latest browser run completed with a 1 ms timer fallback. Per-stage peaks quantize into coarse steps and can exceed 100% when callback timing spans multiple milliseconds. This Chrome AudioWorklet did not expose `performance.now()`, so timing fell back to `Date.now()`; repeated runs can shift a millisecond between processors. Treat these as troubleshooting estimates, not relative CPU benchmarks. Use the high-resolution Linux results in `LATENCY_AND_QUALITY.md` for local DSP comparisons.

The captured non-silent block (sequence 374) reported input peak/RMS `0.38464 / 0.29500` and processed output peak/RMS `0.13480 / 0.07389`; both meters reported zero invalid samples and no clip latch. The latest block (sequence 539) also reported nonzero input and processed output (`0.34998 / 0.26191` input peak/RMS; `0.32316 / 0.14681` output peak/RMS) with no invalid samples or clipping, confirming that the displayed meters follow current worklet blocks rather than freezing the last musical sample.

The browser test captures the processed signal and confirms that the Play output path is connected, but it mutes physical playback during capture. Manual listening through a real browser output device remains open. These results do not establish native hardware or round-trip latency.

Detection was 122.8 ms after playback started in HeadlessChrome 151. The analysis uses a 1,024-sample window (85.3 ms at 48 kHz input / 12 kHz analysis rate) and has a 50–1500 Hz candidate range; native synthetic tests pass at 55 Hz and 1500 Hz, while the exact 50 Hz boundary is unverified. The tester also exposes an optional tuner mute applied after the output limiter with a 10 ms ramp, so delay tails are muted; native automated tests cover the ramp, while actual headphones/speaker listening remains unverified. The browser test confirms the tuning path with a synthesized tone only, not normal pickups, noisy input, chord behavior, or a hardware route.
