## Signal controls

`SignalControls` is shared native C++ code used by the browser/WASM chain. It ramps input mute and global dry bypass over 10 ms, keeps global bypass separate from per-block enable toggles and the dry/wet mix, and applies panic mute immediately with a 10 ms fade-in when released. The focused CTest verifies ramp values, bypass restoration, panic silence/release, bounds, stereo processing, and zero allocations. The latest `make bench` measured 0.0015% p50 / 0.0023% p95 of a 2.667 ms stereo block deadline and 80 B of owned state on the Linux desktop. The browser UI routes toggle messages to the WASM controls; the automated browser parity fixture exercises neutral defaults. Manual toggle interaction and audible behavior remain open.

## Mono/stereo conversion

The shared `convert_channels` helper copies matching layouts, duplicates mono into stereo, and downmixes stereo to mono using the default arithmetic average `(L + R) / 2` or explicit equal-power `(L + R) / sqrt(2)`. Equal-power can exceed full scale; the converter applies no clipping or normalization. It accepts only 1- or 2-channel interleaved float audio and does not resample. It performs no allocation or state update; exact-start in-place conversion is supported while partial overlap is rejected. `tabletfx_offline render` exposes `--output-channels preserve|mono|stereo` and `--mono-sum average|equal-power`. `make test` checks both downmix policies and upmix output. The WASM module exports the same converter and runs an average-upmix/downmix self-check when its AudioWorklet starts. Latest Linux p50/p95 costs for 128-frame stereo blocks are 0.0015/0.0015% for average downmix, 0.0011/0.0015% for equal-power downmix, and 0.0030/0.0034% for mono upmix. Memory cost is 0 B persistent state; caller-provided scratch/output buffers are excluded.

## Input/output metering

The shared `LevelMeter` reports sample peak, RMS, channel count, frame count, non-finite sample count, per-block clipping, a clearable clip latch, and clipped-block count without allocating or locking. It flags digital samples at or above 0.999 full scale; this cannot detect analog clipping inside an interface. Input is measured before input trim/mute, and output after output gain and the optional peak limiter. Two meters occupy 72 B and together measured 0.0154% p50 / 0.0289% p95 of the 2.667 ms block deadline in the latest Linux desktop benchmark. The browser displays peak/RMS in dBFS, clip status, and invalid-sample/frame diagnostics. The automated headless test matched the input meter to the decoded local file and the output meter to the corresponding captured processed block; device-level clip behavior remains unverified.

## Parallel routing primitive (UTL-05)

The shared C++ core now provides an allocation-free two-branch splitter and a dry-plus-two-branch mixer with independent gains, stereo balance, phase inversion, dry-only defaults, and 10 ms control smoothing. It has no algorithmic delay; mixer state uses 112 B. Native CTest covers audio and buffer rules, the WASM module runs a splitter/mixer startup self-check, and `make windows-cross-build` compiles the same code for Windows. Latest Linux p50/p95 is 0.0019/0.0023% of a 2.667 ms stereo deadline for split and 0.0064/0.0071% for mix. This is a tested DSP primitive, not yet a graph-editor/live-routing feature. Browser automation currently verifies the module self-check; it does not expose user-built parallel branches. Native hardware behavior remains unverified.

## Browser/WASM playback

The browser test page for `WEB-01` reads a user-selected local audio file, processes it through the shared C++ DSP compiled as WebAssembly and hosted in an AudioWorklet, and routes Play output to the browser destination. Stop, rewind, block bypass controls, and dry/wet comparison are present. Audio stays local; the page has no microphone or upload path. The delay offers free-time milliseconds or tempo sync (20–300 BPM, 12 divisions); the automated Play fixture selects 120 BPM and an eighth note. `make web-test` passed automated native tests and a headless Chrome run on 2026-11-21.

The browser test uses HeadlessChrome 151, 48 kHz mono, 128-frame blocks (2.667 ms deadline), and a generated one-second guitar-like fixture. Its 25-stage chain enables Input trim, Volume Pedal, High-pass, Low-pass, Noise Gate, Pedal Compressor, Studio Compressor, Wah, Envelope Wah, Clean Boost, Transparent Overdrive, Mid-focused Overdrive, High-gain Distortion, Round Fuzz, Soft Drive, Tremolo, Chorus, Flanger, six-stage Phaser, Vibrato, three-band EQ, tempo-synced Delay (120 BPM, eighth note), Polyphonic Pitch Shifter (+5 semitones), Output level, and Peak Limiter. The fixture selects transparent overdrive at 0.15 drive / −3 dB / 35% wet; mid-focused overdrive at 0.18 drive / +6 dB mid boost / −4 dB level / 40% wet; high-gain distortion at 0.75 drive / 100 Hz pre low cut / 9 kHz pre high cut / 5.2 kHz post tone / −9 dB level / 100% wet; Round Fuzz at 0.55 fuzz / −6 dB / 85% wet; negative flanger feedback; Phaser at 0.5 Hz / 250–1600 Hz sweep / 0.15 feedback / 20% wet; and Vibrato at 5 Hz / 0.35 ms depth / 35% wet. Browser capture compared with the native offline renderer at maximum absolute error 0.00694054 and RMS error 0.000207709 (0.2589% of reference RMS), within the 6% peak and 7.5% RMS full-chain bounds. The C++ chain reports 844,284 bytes plus 10,364 bytes for tuner state, within a fixed 16 MiB WebAssembly linear-memory heap. The automated fixture is generated test audio, not a captured guitar performance; local prerecorded DI pickup samples are separately covered by `make audio-regression`.

The latest browser run completed with a 1 ms timer fallback. Per-stage peaks quantize into coarse steps and can exceed 100% when callback timing spans multiple milliseconds. This Chrome AudioWorklet did not expose `performance.now()`, so timing fell back to `Date.now()`; repeated runs can shift a millisecond between processors. Treat these as troubleshooting estimates, not relative CPU benchmarks. Use the high-resolution Linux results in `LATENCY_AND_QUALITY.md` for local DSP comparisons.

The captured non-silent block (sequence 374) reported input peak/RMS `0.38464 / 0.29500` and processed output peak/RMS `0.14236 / 0.07177`; both meters reported zero invalid samples and no clip latch. The latest block (sequence 539) also reported nonzero input and processed output (`0.34998 / 0.24864` input peak/RMS; `0.49580 / 0.26475` output peak/RMS) with no invalid samples or clipping, confirming that the displayed meters follow current worklet blocks rather than freezing the last musical sample.

The browser test captures the processed signal and confirms that the Play output path is connected, but it mutes physical playback during capture. Manual listening through a real browser output device remains open. These results do not establish native hardware or round-trip latency.

The browser tuner test feeds a separate local 440 Hz tone through Play and verifies the WASM reading (A4 at 440.0 Hz, +31.8 cents with A4 reference set to 432 Hz) and the on-page A4 display. Detection was 122.8 ms after playback started in HeadlessChrome 151. The analysis uses a 1,024-sample window (85.3 ms at 48 kHz input / 12 kHz analysis rate) and has a 50–1500 Hz candidate range; native synthetic tests pass at 55 Hz and 1500 Hz, while the exact 50 Hz boundary is unverified. The tester also exposes an optional tuner mute applied after the output limiter with a 10 ms ramp, so delay tails are muted; native automated tests cover the ramp, while actual headphones/speaker listening remains unverified. The browser test confirms the tuning path with a synthesized tone only, not normal pickups, noisy input, chord behavior, or a hardware route.
